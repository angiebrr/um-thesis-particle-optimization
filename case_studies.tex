\section{Counting Contention}\label{sec:studies_counting_contention}

\addbottomfigure{case-studies_counting-contention}
{0.8}
{The results of "counting the contention" between the background and main threads in \class{Concurrent Particle Data}.}
{The results of "counting the contention" between the background and main threads in \class{Concurrent Particle Data}.}
{fig:CountingContention}

From our initial results, we found that \func{CommitParticleData} was experiencing a great deal of contention. \fig{fig:InitialResultsTiming} showed that, of the 31.5 seconds that \func{CommitParticleData} took, 29.4 seconds was spent waiting for a lock to release. This tells us, then, that it only needed about 2 seconds to do any meaningful work and, if we could reduce this contention, we could speed up that function drastically. The first step in reducing this contention, however, is knowing for certain what is making the background thread in \func{CommitParticleData} wait. 

The simplest way to ascertain what is causing the contention is to do some counting. In \class{Concurrent Particle Data}, we can keep track of an atomic \var{thread counter} which will keep track of how many threads are contending for resources. This \var{thread counter} will be incremented right before a thread attempts to gain access to a lock, and it will be decremented right before it relinquishes access to that lock. The \func{IncrementCounter} and \func{DecrementCounter} methods will print a message when the thread counter is greater than one. During incrementation, a \var{thread counter} that is greater than one means that the current thread is waiting to retrieve the lock. During decrementation, a \var{thread counter} that is greater than one means that another thread is waiting for the current thread to release the lock. Since we have only scheduled one background thread, we know that the \var{thread counter} should never be greater than two.

This "contention counting" was done using the same metadata from \fig{fig:InitialResultsMetrics} in our initial results, and the data collected can be found in \fig{fig:CountingContention}. The functions in which either the background or main threads waited for a lock to release were \func{StartUpdate}\footnotemark $ $ (301 times), \func{Lock} (1 time), and \func{CommitParticleData} (521 times). The functions in which the background or main thread had the other thread waiting for a lock to release were \func{Unlock} (521 times) and \func{CommitParticleData} (302 times). This tells us, then, that \func{StartUpdate} and \func{Lock} were waiting on \func{CommitParticleData} since $ 301 + 1 = 302 $, and that \func{CommitParticleData} was waiting on \func{Unlock} since their counts were both 521.

\footnotetext{Although not a part of the pseudocode provided for the \func{ParticleEffectComponent::OnUpdate} method in earlier chapters, this simple function merely lets the caller know whether or not particle data has been committed since the last time it was called.}

With these results in mind, recall from \sect{ssec:cs_pec_lifecycle} that the \func{Lock} function is used by the \class{Particle Drawable} when drawing particles in order to lock \func{ConcurrentParticleData} and secure access to the particle array. We know from our study of the system that the \class{Particle Drawable} is the only one who uses this \func{Lock} function, and so we know exactly where and how the contention is taking place. We also know that the \class{Particle Drawable} reads information from \class{Concurrent Particle Data}'s particle and new particle indices array. Thus, it is reasonable to say that it is unnecessary to lock both of those data structures at once and, instead, we could try using more than one mutex in \func{CommitParticleData} and \func{Draw} and see if that reduces the contention.

\section{Using More Than One Mutex}\label{sec:studies_mutexes}

% ----------------------------------------------------------------------------------------------------------------------------
\subsection{Code}\label{ssec:studies_mutexes_code}
% ----------------------------------------------------------------------------------------------------------------------------

The changes needed to add mutexes for the two data structures and remaining variables that are copied are fairly minimal. The \var{particlesMutex}, \var{newParticlesIndicesMutex}, and the \var{normalMutex} are added as member variables to \class{Concurrent Particle Data}. Each of these mutexes are locked when their respective variables need to be read or written to. When a mutex is locked within \class{Concurrent Particle Data}, it is done by directly accessing the mutex (see \clis{code:MutexCommitParticleData}). When a mutex is locked within the \class{Particle Drawable}, it is done by utilizing special locking functions\footnotemark $ $ provided by \class{Concurrent Particle Data} (see \clis{code:MutexParticleDraw}).

\footnotetext{In actuality, a single locking function is used. An enumerator is passed to the function specifying which mutex needs to be locked. Although this is better practice, it obfuscates the actual meaning of the code by making it more verbose.}

One of the potential issues with these changes is that, even though a particle is currently active, it may not be available for rendering by the time the \func{DrawParticles} function is called. To more concretely understand, imagine that the \class{Particle Drawable} is taking in new particle indices to activate within the static billboard to make it available for rendering. At the same time, \func{CommitParticleData} was copying new particle data and there happened to be newly emitted particle indices. Since the \class{Particle Drawable} had old information that did not include these newly emitted particles, these new particles will not be rendered because, even though they are marked as active, they are not activated in the static billboard. Although this sounds like a significant problem, we can argue that the inconsistent state cannot possibly be perceived by the user since a considerable number of updates happen within a short span of time. If we look at \fig{fig:Mutex1PESectionCalls}, for example, the number of calls to the \func{Draw} function is about 800, and that is within approximately a $ 20 \ runs * 5 \ \nicefrac[]{seconds}{run} = 100 $ second timespan. This means that this function was called about 8 times per second, and it is highly doubtful that a person could notice the inconsistent state of the particle effect within \nicefrac[]{1}{8}th to \nicefrac[]{1}{4}th of a second. Thus, it is not something that we will worry about.

The figures that focus on the particle metrics \idefine{render ball function calls} and \idefine{particles actually rendered} do not exhibit a great deal of improvement from the original. For both of those figures, improvement would mean higher values. This is because, when more particles are rendered or the ball is rendered more often, the game appears to run more smoothly. Or, in other words, the "frames per second" improves. 

The figures focusing on the particle timing, on the other hand, show considerable improvement. For 0.1 TMP, \func{CommitParticleData} went down from 47 seconds to 24. For 1.0 TMP, \func{ParticleUpdateTask} went down from 50 seconds to 31. This is approximately a 40\% increase in speed!\footnotemark However, we can see that there is still a large amount of contention for the particle array. For 0.1 TMP, 19 of those 24 seconds was spent waiting for the particle array's mutex to unlock. For 1.0 TMP, 29 of those 31 seconds was spent waiting for the particle array's mutex to unlock. It is clear, then, that we should go further in our attempt to reduce contention for the particle array. Instead of adding more mutexes, we could try taking one away.

\section{Using A Lock Free Data Structure}\label{sec:studies_lock_free}

% ----------------------------------------------------------------------------------------------------------------------------
\subsection{Code}\label{ssec:studies_lock_free_code}
% ----------------------------------------------------------------------------------------------------------------------------

A lock free data structure could mitigate the contention for the particle array by getting rid of its mutex completely. Similar to our "multiple mutex" solution, this has the potential problem of the particle array being in an inconsistent state during rendering. However, an analogous argument can be made. Even though the particle array might have partially up to date information during any given render, the renderer is going to update again very shortly and the particle array should be up to date by then. We can know this because \func{CommitParticleData} is called frequently (see \fig{fig:Mutex1PESectionCalls}) and, without waiting for locks to release, \func{CommitParticleData} runs fairly quickly. Therefore, the potentially inconsistent state of particles should not be noticeable to the end user. 

To make the particle array a lock free data structure, we have to first identify which threads are reading and which ones are writing. We know that the main thread (the one that is drawing) is only reading the particles, and we also know that the background thread is writing to the particles. Without a mutex guarding the particle array, there is a possibility that the main thread reads a particle just as the background thread is writing to it. This may result in corrupted data. Thus, a solution in which the two threads can both simultaneously access the array but not the same particle is needed.

There are a variety of strategies that we could employ, but the simplest is to rely on an atomic instruction that is used to achieve synchronization. Specifically, we will use something that is called a \define{compare-and-swap} operation. A \define{compare-and-swap} is an atomic read-modify-write operation on a memory location that can only be implemented using special hardware instructions \cite{Mullender2008Semaphores}. In one atomic action, it compares the value of a variable with what is expected and, once the variable has that expected value, it swaps that expected value with a desired value. Once the atomic operation is attempted, it generally returns a boolean indicating whether or not the operation was successful. A \define{compare-and-swap} operation is typically wrapped within a while loop since it may return false if a concurrent or spurious write occurred. The latter may occur if the value of the variable is actually the expected value but the operation fails anyway. This could happen if we utilized the weak version of \idefine{atomic\_compare\_exchange} \cite{CPPReferenceAtomicCompareExchange}, which is a \define{compare-and-swap} operation defined in the \func{std::atomic} library in C++11. One could utilize the strong version of \idefine{atomic\_compare\_exchange}, instead, in order to avoid spurious writes, but the checks needed within the strong version are expensive. Thus, the weak version can yield better performance if the operation is wrapped within a loop. Due to the infrequency of spurious writes and the small number of threads, the weak version would be the best option in our case. Given that this operation is supported on all of the platforms that ChilliSource supports, the weak version of \idefine{atomic\_compare\_exchange} will be used. 

In order to take advantage of the \idefine{atomic\_compare\_exchange} function, we must use an atomic variable. An atomic boolean was incorporated into \class{Concurrent Particle Data}'s particle struct, as shown in \clis{code:LockFreeConcurrentParticleStruct}. This atomic boolean, \var{isContended}, serves as the variable that the \define{compare-and-swap} operation examines. It indicates whether or not another thread is using this particle struct. When a thread wants access to the particle struct, it calls the \idefine{atomic\_compare\_exchange} function. It will then compare \var{isContended} with "false" and, if it is false, will swap \var{isContended} with "true". The normal particle operations will take place, and then \var{isContended} will be set back to false. Code listings \ref{code:LockFreeCommitParticleData} and \ref{code:LockFreeParticleDraw} illustrate the needed changes in the \func{CommitParticleData} and \func{Draw} functions.

The \var{particles actually rendered} and \var{render ball function calls} figures, similar to the first case study, do not show significant improvement from the original. However, the Lock Free data series in the \var{particles actually rendered} figure seem to have slightly lower numbers than the original, but it is not a significant enough difference to say with absolution that the Lock Free code results in fewer particles being rendered.

As predicted, the timing metric figures show that \func{CommitParticleData} experienced a healthy performance boost. For 0.1 TMP, the function went down from 47 seconds to 15. For 1.0 TMP, it went down from 50 seconds to 7. This is, respectively, about an 68\% and 86\% boost!\footnotemark We see a larger boost in the latter scenario due to the fact that the there are more active particles earlier in the game(s), and so we should expect to see more contention since the draw function needs to render more particles. This will block \func{CommitParticleData} for longer, and minimizing that increased wait time will result in better run times. 

\footnotetext{See \fig{fig:1PECaseStudyLockFreeResults} in \sect{sec:studies_unexpected_results} for a summary table of these timed sections.}

Although these are excellent initial results for the the Lock Free case study, there are two problems:

\begin{itemize}[nolistsep,topsep=0pt]
	\item The particle metric figures did not improve. 
	\item The timing metric are only favorable for a single particle effect.
\end{itemize}

The first problem is an issue because these optimizations should have aided in rendering more particles since updating them takes less time. As for the second problem, we will come to understand in the next section that the two case studies behave quite differently when the games are ran with multiple particle effects instead of just one.

For a single effect, we see that the Lock Free implementation does an excellent job in reducing contention for a large data structure between a background thread writing to it and a main thread reading from it. For ten effects, the Lock Free implementation does little to reduce the contention because there was no contention to begin with. This can be observed by the fact that the results from the Original implementation with ten effects show that, compared with a single effect, an insignificant amount of time is spent waiting for a lock to release.

This behavior can be better understood if we consider the lifetime of particle effects in two scenarios: one with many effects, and one with a single effect. The one with many particle effects would have its particles distributed across many \class{Particle Effect Components} and, thus, many \class{Particle Drawables}. The \class{Renderer} running on the main thread, then, will render each \class{Particle Effect Component} separately. When the main thread requests to lock any given effect's particle array mutex, it has a reduced chance of waiting for it. This is because each \class{Particle Effect Component} has its own background thread and each one is only responsible for a fraction of the particles. The one with a single particle effect, on the other hand, has one \class{Particle Effect Component} with a large array of particles that it has to manage on its own. It can only schedule one background thread at a time and is responsible for updating every single particle. When the \class{Renderer} running on the main thread requests to lock the effect's particle array mutex, it has a greater chance of waiting for it. 

The unexpected results of these case studies demonstrated the differences between managing contention for a single, large data structure and for many pieces or "shards" of a fragmented data structure. The former is likely to have contention if there is writing involved between two threads, and a solution that utilizes "lock free" atomic read-modify-write operations can significantly reduce contention. The latter, however, is unlikely to have contention between two threads, and so the developer can get away with naively using mutexes to synchronize their data.
