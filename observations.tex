\section{Overview}\label{sec:observe_overview}

I performed the optimization case studies in the previous chapter to understand the contention between the main thread that renders particles and the background thread that updates them. This chapter explores various other aspects of \class{Particle Effect Components}. I examined three aspects of the particle effect: (1) the importance of the \var{ConcurrentParticleData} object, (2) the relationship between ChilliSource's \class{Task Scheduler} and \class{Particle Effect Components}, and (3) the perplexing scenarios in which particle effects do not render particles.

\subsection{Overview}\label{ssec:observe_copies_overview}
% ----------------------------------------------------------------------------------------------------------------------------

As discussed in prior chapters, the \var{ConcurrentParticleData} object contains copies of primitives, objects, and data structures needed by the \class{Particle Drawable} to render the particles. It also handles all of the locking necessary in order to synchronize the background and main threads. This section addresses what occurred when \var{ConcurrentParticleData} was not used and the member variables within \class{Particle Effect Component} were instead directly used by the \class{Particle Drawable}. 

The results showed that using the \var{ConcurrentParticleData} object for a single particle effect shifts the heavy contention to itself instead of the \class{Particle Drawable}. In other words, if the \var{ConcurrentParticleData} object was not used during a game with a single particle effect attached to the ball, then the \class{Particle Drawable} would take on the contention that was observed earlier on this paper. For 10 particle effects, however, there was not any contention to begin with so using the \var{ConcurrentParticleData} object made little difference.

\subsection{Code}\label{ssec:observe_copies_code}
% ----------------------------------------------------------------------------------------------------------------------------

There were a considerable number of changes that were needed to remove \var{ConcurrentParticleData} from the \class{Particle Effect Component} and \class{Particle Drawable} classes:

\begin{itemize}[nolistsep,topsep=10pt]

	\item Modified the \class{Particle Drawable} to use pointers from the \class{Particle Effect Component} and removed the \var{ConcurrentParticleData} member variable.
	\item Added variables that \var{ConcurrentParticleData} was keeping track of.
	\item Added functions that \var{ConcurrentParticleData} provided. (Which primarily included accessor and locking/unlocking functions)
	\item Modified \func{ParticleUpdateTask} to update member variables from the \class{Particle Effect Component}.
	\item Modified the \class{Particle Effect Component} and \class{Particle Drawable} to utilize locks and mutexes in order to ensure thread safety.

\end{itemize}

The majority of the above changes are described in Code Listings \ref{code:WithoutCPDParticleUpdate} and \ref{code:WithoutCPDParticleRender}, but it is also necessary to expand on some points. 

In addition to keeping track of information needed for rendering, \var{ConcurrentParticleData} has two booleans that the \class{Particle Effect Component} uses for scheduling updates: \var{hasActiveParticles} and \var{isUpdating}. These booleans describe whether or not there are any particles active in the effect and if \func{ParticleUpdateTask} is running, respectively. If \var{hasActiveParticles} is false when the component is updating on the main thread, then the component stops\footnotemark $ $. If \var{isUpdating} is false when the component is updating on the main thread, then the component schedules a \func{ParticleUpdateTask}. In order to replace this functionality from \var{ConcurrentParticleData}, I added these booleans to \class{Particle Effect Component} as atomic booleans passed by reference to the \func{ParticleUpdateTask} function.\footnotemark

\addtocounter{footnote}{-1}\footnotetext{The particle effect will only completely stop if \var{looping} is false as well.}
\addtocounter{footnote}{+1}\footnotetext{These booleans are not shown in the pseudocode for simplicity, but their behavior is simple; \var{hasActiveParticles} will switch to false if it did not update any particles in \func{ParticleUpdateTask}, and \var{isUpdating} will switch to false at the end of \func{ParticleUpdateTask}.}

Since the \class{Particle Effect Component} uses the bounding information objects on the main thread and the \class{Drawable} does not, I created two mutexes for the bounding information and the rest of the rendering data. 

As shown by \clis{code:WithoutCPDParticleUpdate}, the \func{ParticleUpdateTask} is locked by a member variable mutex. It also passes references to new particle indicies (i.e. \var{copiedAtts.newParticleIndices}) and to the bounding information (i.e. \var{copiedAtts.AABB} and \var{copiedAtts.Sphere}).

\subsection{Discussion}\label{ssec:observe_copies_discussion}
% ----------------------------------------------------------------------------------------------------------------------------

The \idefine{particles actually rendered} (\fig{fig:Copies1PERenderBallFunctionCalls}) and \idefine{render ball function calls} (\fig{fig:Copies1PEParticlesActuallyRendered}) charts for 1 particle effect show something interesting. The No Object data series (the data series without the \var{ConcurrentParticleData} object) rendered the ball fewer times than the original, and it also rendered its particles fewer times. An examination of the timing metrics for 1 particle effect (\fig{fig:Copies1PETimedSections}) shows why this was occurring. Instead of the background thread waiting for the mutex to release in \func{ParticleUpdateTask}, the contention had moved to the \class{Particle Drawable} in the \func{Draw} function.  

If we further examine \fig{fig:Copies1PETimedSections}, it shows that the \func{Draw} function in the No Object data series spends less time rendering than the Original data series. Although a lower run-time usually means that the engine is performing better, it is not true in this case. I did not decrease the amount of time that it takes to render all of the effect's particles and, for the single-burst (PPE is 1.0 of TMP) particle effect, only 72 - 33 =  39 seconds of meaningful work was done since the rendering thread spent about 33 seconds waiting for a lock to release. Since it spent less time in the \func{Draw} function, it rendered fewer particles. 

In other words, the \class{Concurrent Particle Data} object improves performance by increasing the number of particles that are drawn to the screen which results in a smoother visual experience for the end user.

The charts for 10 particle effects, however, do not demonstrate this performance benefit. Both the Original and No Object data series show nearly identical results. This is because there was less overall contention when the particles were distributed across effects, as discovered in the previous chapter. Although the benefits of using a \var{ConcurrentParticleData} object was not as significant when using many particle effects, it is appealing from a software engineering perspective. Encapsulating the thread synchronization to a single class is clearer and more maintainable, and that will be useful if the developer desires to refactor the \class{ParticleEffectComponent}.

The \idefine{small task}, however, is not hindered by any restrictions; this task can be scheduled and ran concurrently alongside the rendering thread. A \func{ParticleUpdateTask} that is not scheduled as a background thread, however, forces the rendering thread to wait and thus no concurrent work is done.}
	{fig:TasksSimpleLifetime}

\end{figure}


As mentioned earlier, \func{ParticleUpdateTask} is scheduled as a background thread by ChilliSource's \class{Task Scheduler}. The \class{Task Scheduler} can schedule a variety of task types, and this section will delve into the different outcomes when \func{ParticleUpdateTask} is scheduled as a \idefine{small task}, a \idefine{game logic task}, and if it is not scheduled at all and runs on the main thread. The results of this study showed that using a \idefine{small task} to schedule a background thread to execute \func{ParticleUpdateTask} yielded much better results than two alternatives (i.e. scheduling a \idefine{game logic task} or not scheduling it at all).  

A \idefine{small task} is considered to be a task with a short execution time such that it can be processed within a single frame, where "a single frame" is the time it takes for the engine to propagate all of its \phase{Update} events from its \class{Application Systems}, \class{States}, \class{Entities}, \class{Components}, and so on (see \sect{ssec:cs_pec_lifecycle}). If a \idefine{small task} runs too long, then the task will have a negative impact on the overall performance of the program. A \idefine{game logic task} is a special kind of \idefine{small task} that is guaranteed to be executed prior to \idefine{main thread tasks}. It is easy to see, then, that long running \idefine{game logic tasks} will drastically affect the program's performance. \idefine{Main thread tasks} are also \idefine{small tasks} that are executed on the main thread after \idefine{game logic tasks}. \idefine{Main thread tasks} are executed by the main \class{Application} instance, and these are typically scheduled by background tasks to complete I/O jobs or any other job that needs to be sequential. All of these tasks are added to \class{Task Pools}, which are a collection of tasks that are performed by one of the worker threads owned by the pool. These pools will continue to perform tasks until they are deallocated and, if there are no more tasks to perform, they will sleep until another task is added.

\subsection{Discussion}\label{ssec:observe_threads_discussion}
% ----------------------------------------------------------------------------------------------------------------------------

For a single particle effect, the Not Threaded and GameLogicTask data series shared nearly identical values (Figures \ref{fig:Tasks1PERenderBallFunctionCalls}, \ref{fig:Tasks1PEParticlesActuallyRendered}, \ref{fig:Tasks1PESectionCalls}, and \ref{fig:Tasks1PETimedSections}). They rendered the same amount of particles, they rendered the ball just as many times, and they spent the same amount of time in various parts of the code. This shows that, at least in the case of a single effect, the main thread waited about the same amount of time for the \idefine{game logic task} as if it was not even threaded.

For multiple particle effects, on the other hand, the overall performance of the Not Threaded data series was worse than the GameLogicTask data series (Figures \ref{fig:Tasks10PERenderBallFunctionCalls}, \ref{fig:Tasks10PEParticlesActuallyRendered}, \ref{fig:Tasks10PESectionCalls}, and \ref{fig:Tasks10PETimedSections}). Although the timing metrics between the two data series were not too different, the particle metrics showed that the Not Threaded data series rendered fewer particles and the ball was not rendered as many times. These results revealed that being able to process multiple effects at the same time before executing the main thread tasks proved to be more efficient than processing them sequentially. 

The results of this particular study demonstrated that scheduling background tasks may not necessarily be faster than its single-threaded implementation depending on how they are organized. Although it may seem obvious, it showed that being able to process many small tasks at once is more efficient than processing a single large task. As a software engineer, it is important to understand the lesson that these results teach. That is, forcing a multi-threaded solution on a problem that does not easily lend itself to doing many small tasks at once may not yield optimal results. In general, a multi-threaded program often requires a considerable amount of overhead and is challenging to debug. Thus, it is critical to structure multi-threaded programs such that it leverages these strengths. ChilliSource achieves this by creating a system that is built to update many \class{Particle Effect Components} at once in background threads.

\subsection{Render Failure}\label{ssec:observe_emit_failure_failure}
% ----------------------------------------------------------------------------------------------------------------------------

\addtopfigure{observation-studies_emission-failure_looping-non-looping}
{1.0}
{Demonstrates the difference between looping and non-looping particle effects that both have a duration of 3 seconds.}
{Demonstrates the difference between looping and non-looping particle effects that both have a duration of 3 seconds. Each particle effect emits once every second, but the non-looping particle effect will stop emitting after 3 seconds have elapsed. It's important to note that, although the non-looping particle effect has stopped emitting, ChilliSource will continue to render any active particles on the screen from previous emissions. The engine will only clean up the particle effect if there are no longer any active particles on the screen.}
{fig:FailureLoopingNonLooping}

\class{Particle Effect Components} sometimes failed to render particles during automated games. When this behavior was observed, I added particle metrics \idefine{particles actually rendered} and \idefine{particles actually emitted} to the instrumentation systems in order to numerically quantify (and, perhaps, understand) the failure. Two main variants of this failure emerged:

\begin{enumerate}[nolistsep,topsep=0pt]
	\item Particles were slow to emit, and it may look like it never emitted if the game's duration was too short
	\item Particles never emitted even if the game's duration was lengthened significantly
\end{enumerate}

The first variant usually exhibited a low \idefine{render ball function call} metric, i.e. a low frames per second, while the second variant did not seem to suffer from a performance hit in the slightest. The first kind was, in a way, expected for particle effects with a large number of particles simply because the renderer was slowed by the sheer number of iterations it was forced to make every update cycle. The second kind, on the other hand, was puzzling because it was not expected behavior. For reasons that will be explained later on in this chapter, the particle effect never emitted any particles in the second variant because the effect met two conditions:

\begin{itemize}[nolistsep,topsep=0pt]
	\item The effect's duration elapsed
	\item There were no active particles
\end{itemize}

This was found to be due to the particle effect having a small duration, a large number of particles, and it was not "looping". Since this was an important distinction between the results of the two variants during this study, it is important to understand what "looping" means in the context of a \class{Particle Effect Componant}. A looping particle effect will continue to draw and update itself even after its duration has elapsed, while a non-looping particle effect will stop drawing and updating once its duration has elapsed. \fig{fig:FailureLoopingNonLooping} illustrates the difference between looping and non-looping particle effects.

% ----------------------------------------------------------------------------------------------------------------------------
\subsection{Emission Failure Solution}\label{ssec:observe_emit_failure_solution}
% ----------------------------------------------------------------------------------------------------------------------------

Discovering why this failure occurred was a multi-step process. The automated game was set to run with a single effect with PPE at 1.0 TMP and a particle value of at least 30,000. Since this seemed to be a rendering issue, breakpoints were set in the \func{Render} function within the \class{Particle Effect Component} class. I discovered that the \func{Render} function inside of a \class{Particle Effect Component} was never called during a game with a single effect with PPE at 1.0 TMP (single-burst) and a particle value of at least 30,000. To further investigate, breakpoints were placed within the renderer itself when it iterated over \class{Render Components} and, specifically, when it iterated over a \class{Particle Effect Component}. It turned out that the effect was being "culled", or ignored, because the bounding information associated with the effect was set to its initial value: \var{INTEGER\_MAX}. Since the actual, non-default value of its bounding information was set inside of \func{ParticleUpdateTask}, this suggested that \func{ParticleUpdateTask} was not being called anymore. Placing breakpoints within the \func{Update} method in the \class{Particle Effect Component} revealed that it called the \func{Stop} function and ceased to schedule \func{ParticleUpdateTask}. As mentioned earlier, this was called because the effect met two conditions:

\begin{itemize}[nolistsep,topsep=0pt]
	\item The effect's duration elapsed
	\item There were no active particles
\end{itemize}

These conditions were met because \func{ParticleUpdateTask} had not updated or activated any particles within the effect's duration time, which was 1 second. This can happen if the main thread that schedules the \func{ParticleUpdateTask} runs again before the \func{ParticleUpdateTask} finishes its first update. This results in the main thread stopping the particle effect because it thinks that the particle effect is done running (i.e. it saw that there were no active particles and the effect's duration elapsed). Thus, it can be inferred that a non-looping particle effect coupled with a small duration and a large number of particles resulted in particle failure. Increasing the duration of a such a particle effect should fix the problem.

The following figures (Figures \ref{fig:FailureSolution1PERenderBallFunctionCalls}, \ref{fig:FailureSolution1PEParticlesActuallyRendered}, \ref{fig:FailureSolution10PERenderBallFunctionCalls}, \ref{fig:FailureSolution10PEParticlesActuallyRendered}, \ref{fig:FailureSolution1PESectionCalls}, \ref{fig:FailureSolution1PETimedSections}, \ref{fig:FailureSolution10PESectionCalls}, and \ref{fig:FailureSolution10PETimedSections}) present metrics that compare the emission failure from above with the solution to that failure. The metrics from this "Solution" data series are the result of running the same scenarios as above (see \sect{ssec:observe_emit_failure_source}) with a non-looping particle effect, but this non-looping particle effect had an increased duration time of 120 seconds\footnotemark. An examination of these results shows that this solution did indeed solve the problem. Particles were rendered from 0 to 50,000 total maximum particles, and a healthy amount of time was spent within \func{ParticleUpdateTask}, as expected.

\footnotetext{Since a duration of any given game was only 5 seconds, a particle effect duration of 120 seconds is overkill. I set the effect's duration to this high number to be certain that it was a small duration number that was causing the particle emission failure behavior. Note that this is separate from the lifetime of a particle itself; the duration that is being referred to here is the duration of the particle effect as a whole and not the lifetime of a particle individually.}

This study has shown that, when using a non-looping particle effect with a large number of particles, a large duration value should be set as well. Although this may seem like ChilliSource should disallow this from happening, it is also true that this resulted from a misconfiguration of a particle effect. At least in the context of the \class{Particle Effect Components} in ChilliSource, a game developer should not expect that a particle effect duration of a single second is reasonable for a particle effect with at least 30,000 particles. However, it would still be useful to at least have a warning printed to the console that informed the developer that a "failing" or "broken" particle effect may be due to a small duration time.
